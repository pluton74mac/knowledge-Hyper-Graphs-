# W9: `queue/`, the queue schema and layer Q

Step W9 of the [Implementation plan](../DESIGN.md#implementation-plan): the C3 queue `khg-queue/1.0.0` (§7). It
builds queue I/O and the packaged queue schema, the state fold, `make_candidate`, the `Queue` handle (`create`,
`open`, `submit`, `accept`, `reject`, `flag`, `verdict`, `withdraw`), the structural `Linter`, `replay` with a base
and `decision_hash`, `queue_items`, and layer Q of the validator. It closes **G3**, and the 17 Q cases of G2 now
pass. It ports `build_examples.py` (the smoke queue, the candidate, the accept and `decision_hash`) and
`khg_validate_proto._q` and `_replay`; the queue schema starts from [DB]'s `khg-queue-1.0.0.schema.json`, renamed to
the lines of §7.

The tree held partial W9 work from an interrupted attempt (the orchestrator's checkpoint commit 388c594 preserved
it). It was reviewed module by module and kept where it was right; the changes are listed under "Decisions". Nothing
in DESIGN.md, `design-examples/` or `research/` was edited. Where DESIGN.md is silent, the decisions follow the
prototype and the committed smoke files.

## Decisions

### The queue schema and its codes

- **Generated, not hand-written.** `queue/codegen.py` builds it with W2's helpers (`X`, `iff`, `propagate`,
  `absolutise`, `render`) and the vocabulary of `queue/model.py`. A test checks that the packaged file is its output.
  It lives in `queue/`, so W2's `schema/codegen.py` stays unchanged.
- **Codes.**
  - Q003: an unknown line kind (or none), item kind or action.
  - Q001: the extraction fields (`run.run_id`, `run.order_id`, `run.position`, `submitted_by` as
    `"<agent>/<version>"`, `doc.doc_id`, `doc.doc_sha256`) and the payload's evidence (present and non-empty).
  - Q002: the payload's `status` and `id` form.
  - Q004: the lint fields (`rule_set`, `findings` as `{code, severity, path, message}`, `outcome`).
  - Q005: a state outside the vocabulary. Q010: the `keys` block, which is required (the §7 table gives Q010 on that
    row).
  - Q008: everything else, such as a missing `payload` or `submitted_at`, unknown fields, a bad id or timestamp
    form, a verdict `other` without `note`, an accept without `before`, `after` or `decision_hash`, and a missing
    `reason`.
  - Item `entities` are `$ref`s into khg-record's `entity`, so their findings carry C codes.
- **What stays in Python:** the fold, the ids scoped by the queue, keys and event hashes, the document, entity
  resolution, the base and the replay (the prototype checked everything in Python).
- `run.model` is a string, like the evidence activity's `model`. §7 does not give its shape; [DB] had an object.

### The fold

- **The move table is the prototype's.** `lint` moves pending to linted, needs_review or rejected; `accept` moves
  linted or needs_review to accepted; `reject` works from any open state; `flag` from pending or linted; `withdraw`
  from any open state. A `verdict` keeps the state and is refused on a withdrawn item.
- **An accept while the item's lint recorded an error finding is Q005.** This is the registry's "accept with an open
  error finding"; v1 has no `auto_fix` that could close one.
- **Q005 and Q007 fold differently, as in the prototype.** A Q005 entry is folded without moving the state, so the
  next entry names it as its parent. A Q007 entry (unknown target, or a parent that is not the item's previous
  entry) is left out.
- **Ids are checked against the header's `queue_id`** only when that id is valid. Otherwise the header's own Q008
  says it once, not once per line. A qid or lid used twice is Q008 and is left out.
- A file whose line 1 is not the header gets Q008 and nothing else (MC170).

### `Queue`

- **Every line is canonical JSON** (`jsonio.canonical`) and ends with a newline. It is checked against the queue
  schema and the fold (and verdict lines against their item) before it is written, so a refused call writes nothing.
- **`submit`** numbers qids `q:<queue_id>.<seq>` (six digits, as in the smoke file) after the largest in the file. It
  refuses an item line that fails the queue schema (Q001-Q003, Q008, Q010, the C codes of an entity), a candidate id
  of another queue (Q002), and a payload whose keys cannot be computed (S001, or C codes). The payload's own C and S
  checks belong to the linter, so a candidate that fails them is logged as rejected, not refused at the door.
- **`accept`** checks the entry before it writes. `before` holds the current versions of the ids the put names (the
  item's entities and the fact), read before the write. `after` holds the versions the receipt says were written;
  no-ops are left out. `decision_hash` covers `after`, read back from the store. With `at=None` the entry takes the
  receipt's time. A store error propagates, and nothing is logged.
- **Actors.** A string is a person (mode `manual`). An object `{type, id, version?}` is used as given; a person is
  `manual` and the other types `automatic`. `at` defaults to `SystemClock` (RFC 3339 UTC, microseconds).
- **One appender at a time.** A handle remembers the file size it last read or wrote. If the file changed, the next
  append raises `ConcurrencyError` (no code is registered for this; D019 is the store's `expect`). A file without a
  final newline gets one before the next line.
- **`open` is strict.** Any structural error, a schema pin that differs (D009) or a base that does not match (Q012)
  raises. So a handle only ever appends to a valid file.

### `Linter`

- **Outcomes.** `fail` when a finding is an error (the item goes to rejected), `warn` when one is a warning
  (needs_review), else `pass` (linted). §7 names the states but not this mapping.
- **Findings** are recorded as `{code, severity, path, message}`, with paths relative to the item. They come in rule
  order: the item line against the queue schema, then C, S020 and S on the payload, then Q002, Q009, Q010 and Q011.
- **The base lint loads first** is a container given as `entities` under the header's base `document_id`, else the
  queue's base. It must match the header. If it does not, `lint` raises `ValidationError` (Q012) and logs nothing.
  When the header names a base and the linter has neither it, entities nor a store, `lint` raises Q012 too. A
  caller's missing base would otherwise log a failed lint and reject the item for good. D009 (another schema), Q007
  and Q005 are raised the same way.
- **Resolution order** is `item.entities`, then the linter's `entities`, then the base's latest entity records, then
  the store. Fact values resolve from the base, then the store; a fact nobody resolves is not judged (S005 needs it).
- `doc_texts` follows the validator's rule (a mapping, a `khg-doc-texts` document or a path) and reuses its reader.

### `replay`

- **The base is loaded before the first accept**, at the header's `created_at`, or 1 µs before the first accept if
  that is earlier, on a `ScenarioClock` starting there. A load is a write (W8), and the store's transaction time only
  moves forward. The prototype and W8's test used `2000-01-01T00:00:00Z`; any earlier instant gives the same hash.
- **Each accept is re-run** as one `put` of the item's entities and the payload with the fact's id, at the entry's
  `at`, by the entry's actor. The fact's id is the one id of `after` and `before` that is not an item entity. If there
  is no such id, or more than one, the result is Q006.
- **Findings.** A failed put, an `after` that differs, and a recomputed `decision_hash` that differs are each Q006.
  Before the replay, the file's structure, D009 and Q012 are checked; if any is an error, nothing is replayed.
- **The result** is `{ok, findings, decisions: [{lid, target, after, decision_hash}], store}`. `store` is the
  replayed store, or None when nothing was replayed. `replay` raises only for a file that does not parse or a bad
  schema or base argument.

### Layer Q

- **Order of checks.** The fold with the schema; then Q012; then the item and verdict checks; then, only when none of
  these is an error, the replay on `memory_factory` (the prototype's rule). So MC173's changed event hash is Q010
  alone, not Q010 and Q006.
- **Q012 when the header names a base that `bases` does not supply**, or supplies with another sha256. The prototype
  does the same. Entities then resolve from `item.entities` only, which gives MC175's Q011.
- **D009 is never reported by layer Q.** The header pin is `d_container`'s (W5). A missing schema is reported by the
  next step that asks (layer S). Layer Q reads `ctx.schema` without resolving it. It skips the key checks and the
  replay under a schema the header does not pin, so D009 is the only finding then and the first layer is D.
- **An invalid payload with an accept can give Q006.** If a payload fails C or S and an accept of it is logged, the
  replay's put fails, and that is Q006 at layer Q, ahead of the C or S finding. The log claims a write the store
  refuses, which is a replay mismatch (the prototype behaves the same). No case of the list has such a queue.

### Verdicts and `make_candidate`

- **Verdicts judge extracted or inferred evidence only.** Evidence without an `event_hash` cannot key one, so it is
  Q008.
- **Comparisons.** The verdict's `core_key` is compared with the item's stored `keys.core_key`, which is what
  `queue_items` attaches verdicts by. Binding labels name payload bindings by (role, position, value identity); the
  bid is not checked, being only a hint.
- **`Queue.verdict`** fills `core_key` and `event_hash` when they are absent, and defaults `bindings` and `missing`
  to `[]`. Values that are given are kept, and then checked.
- **`make_candidate`** drops the store fields, `derived` and evidence `recorded_at`. It assigns each binding without
  a bid the smallest free `b<n>`, in listed order, sets the id and status, normalises the record (so `supports`
  defaults to every bid), and stamps missing event hashes. A stored event hash is never replaced (§2.9); the linter
  reports a wrong one as Q010. It validates nothing else.

## Deviations from DESIGN.md

- **`Queue.open(path, *, schema, base=None)`.** §7 has `Queue.open(path, *, schema)`. The optional `base` lets a
  reopened queue lint against its base; a base given must match the header (Q012). Without it, the linter takes the
  base as `entities` (the P9 sequence of §1.3 does exactly this).
- **Additions beyond §7.**
  - `Queue.path`, `queue_id`, `header`, `schema`, `base`, `qids`, `state(qid)`, `item(qid)` and `__fspath__`, so a
    handle is read wherever a path is.
  - `queue.verdicts.aggregate` and `complete`, and `queue.codegen`.
  - The helper modules `model`, `lines`, `fold`, `checks`, `decision`, `items` and `replay.replay_accepts`.

  None is in `queue.__all__` beyond §10.2's names and `FORMAT`.
- **`Linter.lint` raises Q012 and D009 before logging** instead of recording them as lint findings (see
  "`Linter`").

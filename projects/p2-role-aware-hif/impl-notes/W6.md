# W6: `hif/` and validator layers H, R, P and decoding D

Step W6 of the [Implementation plan](../DESIGN.md#implementation-plan): `to_hif` (literal labels, literal nodes shared
by value or per binding, weights, binding extensions, closed slices, the inlined schema), `from_hif` (decoding, D009
without a schema), the `khg-hif/1.0.0` profile checks, layer R (`role-convention` 1.0.0) and layer H (the vendored HIF
schema through the closed resolvers of `validate/engines.py`). It ports `khg_synth.c1_to_hif`, `select_slice` and
`hif_to_c1`, and `khg_validate_proto._h`, `_r`, `_p` and `_decode`. Where DESIGN.md was ambiguous, the decisions below
follow `design-examples/` and the synthesis prototype. Nothing in DESIGN.md, `design-examples/` or `research/` was
edited.

## Decisions

### `to_hif`

- **Signature** as §4.2: `to_hif(container, schema, *, relations=None, literal_nodes="shared",
  schema_document=False) -> dict`. `container` may also be a path (`record.read_container`), and `schema` a schema
  document or a path (`load_schema`: J, V, M), as elsewhere in the package.
- **Refusals, with registered codes** (`ValidationError`; the prototype raised only for bad literals, undeclared
  relations or roles and P003):
  - D009 when the header's `schema` block pins another schema (id, version or sha256) than the `schema` argument.
    The prototype silently re-pinned the file to the argument; the directions would then come from the wrong schema.
    A header without a `schema` block takes the argument's.
  - D001 for an entity id or a hyperedge id declared twice. This refuses history containers, which HIF cannot hold
    (the prototype wrote duplicate edges). An entity and a hyperedge sharing an id pass through (HIF keeps nodes and
    edges apart); `validate_container` reports D007.
  - S001 for a relation in `relations` that the schema does not declare (the prototype exported an empty slice for a
    typo). `relations` given as a string is `TypeError`; repeats are dropped (`khg-slice` lists each relation once).
  - C010 for a structure `to_hif` cannot read: no `{header, records}`, a header `format` or `document_id` that is not
    a string, a record without a string id, a hyperedge without a relation or with bindings lacking `bid`, `role` or
    `value`, an `extensions` that is not an object. The value codes (C001, C002, C004, C010, S006) come from
    `record.canonical_value`.
  - P008 for a key of `extensions["hif:metadata"]` that would clash with the declaration block (a key of §4.5,
    `default_attrs` or any `khg-*` key). The prototype copied those keys last, so they overrode the declaration.
- **An empty `extensions` object is kept** as `khg-extensions: {}`, so it round-trips; the prototype dropped it.
  `extensions` holding only `hif:weight` still becomes a weight and no `khg-extensions`, as in the fixture.
- **Key order in edge `attrs`** follows the §4.2 table (`khg-evidence` before `khg-typed-under`, `khg-version`, ...);
  the prototype wrote the store fields first. Equality is structural (F10), and the fixture has neither.
- **An entity's `recorded_by`** is not exported: §4.2 lists `khg-version` and `khg-recorded-at` for entity nodes but no
  `khg-recorded-by` (edges have it), and the prototype agrees. `compare_containers` ignores store fields, so G1 is not
  affected. See "Observations" below.

### Decoding and `from_hif`

- **`from_hif(hif, schema=None)`** as §4.3. `hif` is a document, raw `bytes` or a path (layer J's `parse`). It runs
  `validate.run(..., steps=("j", "v", "h", "r", "p"), stop="first")`, then resolves the schema through
  `Context.relation_schema()` (the argument, else `khg-schema-document`, whose V and M findings are raised, else
  D009), then `decode`. It raises `ValidationError` with the codes of the first failing step, or of decoding.
  **It returns the canonical container** (`record.canonical_container`); the prototype returned records as decoded,
  and its checks canonicalised them before comparing.
- **`decode(hif, schema) -> (container | None, findings)`** reports every problem it finds; the prototype raised at the
  first one. Each HIF case of the list still gives exactly its `reported` codes. The container is None when a finding
  is an error. It is the container as written (entities in node order, then hyperedges in edge order, bindings in
  incidence order), not normalised, so layer S still reports strings that are not in NFC (S020); `from_hif`
  normalises.
- **What decoding checks beyond the prototype**, each under the code its registry entry names:
  - D009 compares `khg-schema` with the schema's `<id>/<version>` as well as `khg-schema-sha256` (the registry's
    meaning names id, version and sha256; the prototype compared the digest only).
  - Every literal node's `khg-literal` must be a well-formed literal, whatever its prefix; its own codes (C002,
    C004, S006) are reported at `/nodes/<j>/attrs/khg-literal`. The prototype only canonicalised `_:lit:` literals
    (for the digest) and passed `_:litb:` literals through.
  - A `khg-extensions` that is not an object while the record also has a `weight` to merge is C010.
  - S001 (undeclared relation, once per edge) and S002 (undeclared role) are reported while decoding, because the
    decoder needs the usage to drop default directions; the prototype raised them from `Schema.usage`.
- **Paths.** Findings point at the fault: `/nodes/<j>/node` (D001, D005), `/edges/<k>/edge` (D001),
  `/incidences/<i>/edge` (D003), `/incidences/<i>/node` (D002, D005), `/incidences/<i>/attrs/khg-bid` (P016),
  `/incidences/<i>` (P010), `/incidences/<i>/direction` (S016), `/metadata/khg-schema` and
  `/metadata/khg-schema-sha256` (D009). The prototype reported decoding findings at `""`.
- **Unknown attrs are dropped** on decode, as in the prototype: node and edge attrs outside the §4.2 maps, incidence
  attrs other than `role`, `role-position`, `khg-bid` and `khg-extensions`, and weights on derived nodes. The profile
  refuses only unknown `khg-*` keys in metadata (P008) and incidence attrs (P014).

### The validator layers

- **H** runs on `hif` and `role-convention`; **R** on both; **P** on `hif`. H and P run the packaged schemas through
  `engines.findings`, so both engines, the closed resolvers and the H table are W4's.
- **P drops layer H's findings** (the profile schema `allOf`s the vendored one). With fastjsonschema, which stops at
  its first violation, a file with an H error therefore gets no schema finding from P (the vendored branch fails
  first); jsonschema reports both. Single-fault containment holds on every case.
- **Decoding reads only files that passed H, R and P.** H, R and P record their outcome in
  `ctx.state["hif_layers"]` (letter -> no error) through `d_decode.note`; `d_decode` decodes only when all three
  passed, and checks any of them that did not run in this run (a `steps` subset) without reporting. So a P case
  reports its P findings once: the prototype's decoder repeated P010, P016 and P017, but its harness stopped at the
  first rejecting step and never showed the repeats. After an H, R or P error the full report holds no C, S or D
  finding either, since nothing was decoded. The key is documented in `d_decode.py`; `validate/context.py` (W4) was
  not edited.
- **`d_decode` uses `ctx.relation_schema()`**, so the D009 of a run without any schema is reported once, by
  decoding, at `/metadata/khg-schema` (S and `d_container` then find the schema resolved). An invalid inlined schema
  gives its M findings at `/metadata/khg-schema-document/...`, and M ranks after the pipeline's letters (W4's rule).
- **R004 reads an integral float as its integer** (`1.0` is position 1), as F10 and the rest of the package do
  (JSON Schema's `integer` accepts it, and canonical JSON writes `1`). The prototype refused `1.0` with R004. The
  R002 key uses the same reading, so positions `1` and `1.0` are an exact repeat. Ids keep their JSON type in every
  key (`1` and `"1"` are two ids).
- **P010 is one finding per incidence without a direction** (`/incidences/<i>`), and P017 is reported at
  `/nodes/<j>/attrs/khg-external`; the prototype gave one P010 at `/incidences` and P017 at `/nodes/<j>`. Codes are
  unchanged.

### Minimal fix to a file of an earlier step

- `tests/validate/test_cases.py` (W4), `test_the_other_bases_pass_the_w4_layers`: it asserted that the HIF bases
  have no finding at all, which held only while H, R, P and `d_decode` were stubs. A HIF run now decodes the file and
  checks it, so the full fixture gives the designed S024 warning and, with W5's layer D, L008 (the slice gives L008).
  The assertion now allows exactly those warnings on the two HIF bases and still requires no finding on the other
  bases and no error anywhere. W5 edited another function of the same file in parallel (the L008 of the C1 bases);
  both edits are in place.

## Observations on the design (no change made)

- **Entity `recorded_by`** is lost by `to_hif` (§4.2 lists no `khg-recorded-by` on entity nodes, though §2.2 gives
  entities that store field). §4.3 says export followed by import gives the same canonical container; for a store
  export that is true only up to store fields, which `compare_containers` ignores. Adding `khg-recorded-by` to entity
  nodes would be a compatible minor change.
- **Dangling references outside a slice.** A valid but incomplete container (no `complete: true`) may reference a
  fact or an entity it does not hold. `to_hif` writes such a fact reference with `khg-external: true`, which P017
  refuses outside a slice, and an absent entity as an incidence to an undeclared node, which decoding refuses (D002).
  So such a container exports, as in the prototype, but does not re-import. A store's `put` refuses unresolved
  references (D002 on writes), but `load` is trusted bulk import, so a store loaded from such a container exports it
  the same way. Raising at export time (D002) would be the stricter reading.
- **`network-type` of a file without incidences** is `directed` (vacuously every incidence has a direction), as in
  the prototype; both values pass the profile there.
- The header fields `as_at`, `created_at` and `generator` have no HIF metadata key (§4.5), so they do not survive a
  round trip; `compare_containers` ignores the last two.

# W11a: C4 and layer I, memory gold, the memory scorer, and G2

This is step W11a of the [Implementation plan](../DESIGN.md#implementation-plan). It builds:

- the checks of the C4 draft `khg-c4-items-0.1.0`, as layer I behind `validate_item`;
- `derive_memory_gold`, as §9.5 states it (normative), replayed on `MemoryStore`;
- the memory scorer: outcomes O1–O7, strict and lenient accuracy, and the stale rate;
- the G2 harness over all 180 malformed cases.

It ports `khg_c5_proto.derive_memory_gold`, `khg_validate_proto._i`, `build_c4.question` and the harness of
`make_malformed.py`. Where DESIGN.md was silent or ambiguous, the decisions below follow `design-examples/`, the
prototypes and R05 §5. Nothing in DESIGN.md, `design-examples/` or `research/` was edited. The one change to an earlier
step's file is listed under "Changes to earlier steps".

## G2 (closed)

`tests/gate/test_malformed.py` (marker `gate`) reads everything from the packaged `data/` files. It builds each case
as §8.2 and the list's `harness` block state:

- the input is the base plus its patch, or `input_text` run as HIF for layer J;
- a `schema_patch` goes on the fixture schema, and the base's digest is re-stamped;
- the context is the case's own `doc_text` and the smoke base as the queue's base;
- the engine is jsonschema, with the full report.

Results:

- **The rule.** All 180 cases are rejected first at their listed layer, with their listed code among the errors. No
  step is skipped.
- **Reported codes.** For all 180 cases, the error codes up to the first rejecting step equal the prototype's
  `reported` codes. A `stop="first"` run returns exactly those findings.
- **Self-checks.**
  - Every patch applies. The machinery is strict: a missing key or index raises, and a test proves it.
  - Every input differs from its base.
  - Every `expect_target` resolves, and it pins exactly the indexed paths of its patch (recomputed with the
    prototype's identity table).
  - Every unpatched base validates with no error under both engines. The only findings are the designed warnings
    S024 and L008.
- **Coverage.**
  - 123 active codes of layers J–I; every one except D019 is listed and detected.
  - Each case's layer is its code's letter.
  - No case yields a reserved, planned or unregistered code under either engine.
  - Nested findings sit only under I003.
  - The list has the §8.2 counts per layer and the validator's pipelines.
  - Every layer module is implemented.
- **Engines.** fastjsonschema rejects every case at the same step and layer, and its codes are contained in
  jsonschema's. The claim "exactly one code at the first rejecting step" (§8.1) holds for the JSON Schema steps. On
  11 cases the first rejecting step is a Python step, and both engines report the same several codes there:
  - S: MC087, MC088, MC103, MC116;
  - D: MC121, MC122, MC133, MC138;
  - Q: MC164, MC174, MC175.

  The test therefore asserts "one code, or the same codes on a Python step".

## Decisions

### Layer I

- **Nesting.** Layer I emits I codes, plus D009 for the schema pin. An I003 finding keeps the inner C, S or D finding
  under `nested`, the convention W11b's `scorers/_inputs.py` set.
  - The draft `$ref`s C1 definitions of `khg-record`, so a malformed embedded value gives a C code there. Layer I
    turns each such C code into I003.
  - The prototype passed these C codes through unchanged. Its layer rule would then have found no I layer.
  - Findings keep §8.1's five keys. `nested` is an extra key, and only I003 findings carry it.
- **The file.**
  - I002: line 1 is not the `c4-header`, or a later line is one.
  - I002: an `id`, `qid`, trace `trace_id` or `doc_id` is used twice. W11b's scorers use I002 for duplicates too.
  - A repeated `trace_id` makes the trace ambiguous, so its questions are not replayed.
  - The prototype did not check any of these.
- **The schema.**
  - Without a schema, layer I reports D009 at `/lines/0/schema`. W4 anticipated this in `Context`.
  - A schema that is not the one the header pins is D009, and the S checks and replays are skipped. This matches
    layer Q's handling of a queue header's pin.
  - The prototype read the schema without checking the pin.
- **Embedded records.** Layer S, with S020, runs on an extraction document's gold and entities, and on a trace's
  entities and `put` records.
  - Only error findings are nested under I003, as in the prototype. A warning constraint, such as S024, does not make
    an item invalid.
  - The gold's spans (S021) are read against the item's own `text`.
  - `apply` events are checked by the store when the trace is replayed. The C4 draft leaves their content open.
- **Replays.**
  - Each trace without an error is replayed once, in full, and every question reads its gold at τ. The prototype
    replayed per question, up to `ask_after_step`.
  - Both give the same gold whenever the full trace replays. A test checks every fixture question at steps 1 and 2.
  - A write that the store refuses is I003 at `/lines/<n>/entities` or `/lines/<n>/events/<k>`, where k is the
    event's index in the file. The store's findings are nested: D014, D018 or C010, for example.
- **Questions.**
  - A question whose trace is not in the file is I003, as in the prototype.
  - A relation, key role or target role outside the schema is I003, with S001 or S002 nested.
  - A step the trace lacks, a relation without a key, or a key that does not bind exactly the key roles is I005:
    "derive_memory_gold cannot replay the question". The prototype crashed on a missing step.
- **I005 compares by value identity.** Each gold field is compared as a multiset of identity keys; stale values are
  compared with their kind.
  - So order and writing do not matter (an NFD id is the same entity), and duplicates do.
  - `answer.text` is not compared, because it is not gold.
  - The prototype compared canonical JSON exactly: order-sensitive, and it flagged any `answer.text`.
  - MC180 and the fixture give the same results under both rules.
  - I005 replays with the default reasons only (§14 question 3). A test shows that a set built with other reasons
    fails I005.

### Memory gold (`derive_memory_gold`, §9.5)

- **The replay.** It is the prototype's, on the package's `MemoryStore`:
  - the entities are put one second before the first step;
  - then each event runs at its `tx_time` with actor `trace:<trace_id>`, in step order;
  - events of one step run in list order, and τ is the step's last `tx_time`;
  - a `ScenarioClock` starts at the entities' time;
  - `store_id` is the default. A `trace:<id>` store id could exceed the store's 500-character limit, and the id
    affects no gold.
- **`derive_memory_gold` replays up to `ask_after_step`**, as the prototype did. It needs only the question's
  `ask_after_step`, `relation`, `key`, `target_role` and `where`, so `build_c4`'s way of filling gold works. It
  refuses a question that names another trace (`ValueError`).
- **Values.** Values are collected in id order. The first writing of a value identity is kept; the prototype kept the
  last, in insertion order. Both orders are deterministic, and the fixture has one writing per value.
  - `unbound` values (goals) are never collected.
  - The sets are sorted by identity key, and stale values list `expired` before `revised`, as in the prototype.
- **Errors.**
  - Store errors propagate unchanged, and `Replay.position` names the write that failed.
  - A relation, key role or target role outside the schema raises `ValidationError` S001 or S002.
  - A missing step, a relation without a key, a wrong key or a malformed `where` raises `ValueError`.

### The memory scorer

**Outcomes.** They follow the probe's precedence (`c5_reference_cases.memory_outcome`): current, then hedged, then
stale, then anachronistic, then wrong. These choices go beyond R05 or clarify it:

| Case | Decision | Basis |
|---|---|---|
| Abstention | The abstain flag, or Â empty (R05's O6) | R05 O6 |
| Â empty, V_cur empty, question answerable | `current`, because the gold is "no current value" (§9.5). Abstaining is `abstained` | R05 did not have this gold |
| Unanswerable question | Abstaining (the flag or Â empty) is `correct_abstention`; answering is `hallucinated` | The probe counts only the flag; M4a and M4b agree |
| A disputed value | Counted in `hits`; it never changes the outcome | R05's rule names only V_old and V_fut |
| A stale answer that hits both kinds | `stale_kind` is `expired`, which wins over `revised` | The gold's own rule |
| A question without a response | `missing` (0, 0), counted in `n_missing` and in no abstention metric | Rewarding silence on unanswerable questions would be wrong. The retrieval scorer also counts missing responses apart |

**Set-valued questions.** The C4 draft has no answer mode, so outcomes use R05's intersection rules. R05's "else
score set F1" is reported beside them: `set_p`, `set_r` and `set_f1` against V_cur, and the aggregate `set_f1` over
the answerable questions, where an abstention or a missing response counts 0.

**Metrics.**

| Metric | Definition |
|---|---|
| `acc_strict`, `acc_lenient` | Pooled over all questions; correct abstentions count 1 (`pooled_abstention: true`, as R05 M-M1 asks) |
| `answerable` | The same accuracies over the answerable questions only |
| Rates of O2–O6 | Over the answerable questions: `stale_rate` (split into `stale_expired_rate` and `stale_revised_rate`), `hedge_rate`, `anachronism_rate`, `abstention_rate` and `wrong_rate` |
| `stale_share_of_errors` | Stale outcomes over the answerable questions with strict 0 (M6: 3/4) |
| Abstention | Precision: `correct_abstention` over all abstentions. Recall: `correct_abstention` over the unanswerable questions. Also `hallucination_rate` |
| `ranked_efficacy` | CounterFact's ES: 1 when the best-scored current value outscores every stale value. An unscored value ranks last, and a tie is 0 |
| `support_success@k` | Against the question's current `support`, for k in `KS` = (1, 3, 5, 10, 20), the retrieval defaults (`MemoryConfig` has no cut-offs). Units are ordered by rank, then input order. Only responses with `retrieved` count |

- **The headline** is `acc_strict`, or `acc_lenient` with `mode="lenient"`.
- **Breakdowns** are by subtype and by relation.
- **The bootstrap** gives intervals of both accuracies, with the question as the unit.

**Tolerance (R05 M-M8).** The draft's `tolerance` is an open object, so the scorer defines one key, `amount`: a
number, or a C1 decimal string, of at least 0.
- A quantity answer matches a gold quantity of the same unit when their amounts differ by at most the tolerance.
- A negative or malformed amount is I002. Other keys are not read.
- M8's "18 days, answer 19" is written as a population of 18.

**Inputs.**
- Items go through W11b's `_inputs.check_items`, the draft schema with C codes as I003, as in the other scorers.
- Outputs go through `check_outputs(kind="memory-response")`.
- Then the scorer runs the replay checks it shares with layer I (`check_question`, `replay_findings`):
  - a missing trace is I003;
  - a store refusal is I003, nested;
  - a disagreeing gold is I005;
  - a repeated qid or trace_id is I002;
  - a repeated response is C010;
  - an answered value whose identity cannot be computed (a year 0, for example) gives its own code, such as S006.

  The two schema checks raise first, as in the other scorers. After them every finding is collected before one
  `ValidationError` is raised. Paths are `/questions/<n>`, `/traces/<m>` and `/responses/<k>`.
- **`incorrect_reasons`.** The scorer replays with `config.incorrect_reasons` and requires the stored gold to agree
  (I005). A question set is scored with the reasons it was built with, which is the reading of ruling 3. A set built
  with the default and scored with another list raises I005, and a test pins this.

**Not scored.**
- Response `cost` is accepted but not reported, because §9.3's memory row has no cost.
- Text-only answers are not mapped to values, because the draft has no aliases. `answer.values` is what is scored
  (R05 D-C5-13).
- Answer entities are resolved through `redirect_to` over the entity records of the replayed trace.

## Deviations and observations

1. **Beyond the prototype (layer I).**
   - I002: the header's position, and ids used twice.
   - D009: the schema pin.
   - Layer S on embedded entities and gold, with the item's own text for spans.
   - Replays of every trace, even those no question names.
   - I005 by value identity.
   - The C codes of the draft become I003.

   The five I cases and the fixture give the same results as in the prototype.
2. **The draft's I004 is wider than its registry meaning.** The packaged `khg-c4-items-0.1.0` gives a memory
   question's `then` the map `{"default": "KHG-I002", "required": "KHG-I004"}` (`make_schemas.py`, the stale_values
   rewrite). So any missing required field of a memory question is I004, and so is a missing `role` or `value` in its
   `key` items; `text` is one example. The registry means only a missing `stale_values` or `future_values`.
   - The schema is packaged, verified data, so layer I reports what it says. A test pins this with a comment.
   - A fix belongs to a minor release of the C4 draft (§11.2; risk 6).
3. **Public names beyond §9.2.** These were added so that layer I, and P7, can share the replay:
   - in `memory`: `Replay`, `replay_trace`, `read_gold`, `check_question`, `gold_findings`, `replay_findings`,
     `classify`, and the constants;
   - in layer I: `item_findings` and `embedded_findings`.

   The two §9.2 signatures are unchanged, and a test checks them.
4. **The tolerance semantics** (`{"amount": d}` on quantities) are the scorer's reading of an open C4 field. P3a owns
   C4, and it may define more keys.

# W8: `store/` and the conformance suite

Step W8 of the [Implementation plan](../DESIGN.md#implementation-plan): the C2 interface `khg-store/1.0.0` (§6). It
builds the `Store` protocol (9 core and 6 derived methods), `Where` and its defaults, `SystemClock` and
`ScenarioClock`, `StoreBase`, `MemoryStore` with the 10 capability flags, header state and the 4 atomic events,
export (khg-json, khg-jsonl and HIF through W6's `to_hif`), `Timed`, `compare_containers`, `load(on_missing=...)`,
and the conformance runner, which runs the packaged scenario files and returns an EARL-shaped report. It ports
`khg_store_proto.py` and `run_scenarios.py`. The invariant, `KeyCollision` and the lifecycle rules are W5's
functions (`record.keys`, `record.lifecycle`); layers C and S are W4's.

Where DESIGN.md was ambiguous, the decisions below follow `design-examples/` and the synthesis prototype. Nothing in
DESIGN.md, `design-examples/` or `research/` was edited. No file of another step was changed: every file of this
step is new, under `src/khg_contracts/store/` and `tests/store/`.

## Decisions

### Where DESIGN.md leaves room

- **Temporal keys and L008 need `valid_time`.** §6.3 lists temporal keys under `valid_time`. A store with
  `key_constraint` but without `valid_time` checks only non-temporal keys and reports no L008. The prototype checked
  temporal keys whatever the flags. Raising `CapabilityMissing` instead would refuse every write of a relation with a
  temporal key, and the scenarios that write `position_held` facts without testing keys (S-VER-003 and others) do not
  list `valid_time`. Every capability-limited run passes.
- **What else needs a flag on reads.** The prototype checked only `valid_time` and `transaction_time`. Following
  §6.3's table, a read also needs `goals` to include status `goal` or to use an `any_unbound` pattern,
  `ordered_roles` for a pattern position, `literal_values` or `special_values` for such a pattern value, `nesting`
  for a fact value in a fact relation's pattern and for `incident(fact id)`, `history_export` and
  `transaction_time` for `iter_records`. No scenario's `requires` misses any of them (the limited runs would give
  `cantTell`).
- **The invariant without an incoming fact** (the gap W5 left to the store). After `keys.collisions`, the store
  compares `keys.key_invariant_violations` before and after the write over the key groups it touches. A new
  violation raises `KeyCollision` with `info = {"collisions": [], "violations": [{relation, key_digest, temporal,
  ids, at}]}`: for example a retraction or dispute that takes away the only preferred fact of a key while two
  normal ones hold. A violation that was already there (after a trusted `load`) is not blamed on a write that does
  not take part in it.
- **The check order** is §6.2's. D019 (`expect`) comes right after the capability checks, and D013 (the version rule)
  after record validation; §6.2 names neither. An id written twice by one call, or named twice by one event, is D001
  ("record declared twice"). `NotFound` carries D002, as the prototype raised D002 for a missing target.
- **Records validated.** Every record a write makes runs layers C and S: new records, new versions, the lifecycle
  records an event builds, and the versions whose status an event changes. Records are normalised first, as the
  store keeps the canonical form, so S020 remains only for keys that collide under NFC. Layer C runs fastjsonschema
  and, when it refuses, jsonschema to list every finding. This is about 10 times faster (0.09 ms against 0.96 ms per
  fixture record). jsonschema accepts every one of the 3,390 versions that the 114 scenario stores hold, and the
  codes of a refused record come from jsonschema.
- **D002 and D020 apply to the values a write adds or changes** (by bid). A new version or event that keeps an
  entity value written before that entity gained `redirect_to` is accepted. The prototype re-checked every binding
  of a new version put. S-PUT-010 (a new record) still gives D020.
- **Receipts** list L008 only, as §6.1 shapes them; layer S warnings such as S024 are not listed. An all-no-op put
  returns `at` = `clock.now()` and does not tick (the prototype). Every write, `add_evidence` included, reports the
  L008 pairs of the records it wrote.
- **The store never stamps evidence `recorded_at`.** S-EXP-002 compares a rebuilt store with the fixture, whose
  evidence has none.

### Events

- Records carried by an event must be new hyperedges arriving as asserted (D014 otherwise); a `status_ref` on them
  is dropped (the prototype). A lifecycle record id that exists is D014.
- A transition to `asserted` accepts `disputed`, `quoted` and `goal` only. W5's `TRANSITIONS` also holds
  (`superseded`, `asserted`) for the undo row, but that change happens only by retracting the lifecycle record.
  `retracted` to `retracted` is D014 (`transition_problem` treats an unchanged status as no move). A transition to
  `asserted` with more than one target needs `atomic_writes` (a multi-record call).
- Undo finds the facts to restore through the `status_ref` index: those whose current `status_ref` names the
  retracted record and that it binds. With `resolve_superseding: "dispute"`, the superseding facts must be able to
  become disputed. The new `khg:disputes` record (`dispute_id`) binds the superseding facts, then the restored ones,
  with reason `key_conflict` and the event's evidence (the prototype).
- `end_validity` needs the flags of `end` and `end_cause` beside `valid_time`. On a superseded or retracted fact it
  is D013 (frozen), and on a quoted or goal fact D014; the prototype gave D014 for both. A relation without an
  interval time model is S002 (the prototype).
- An appended evidence id that the fact already has is D013 (evidence is append-only).

### `load`

- It keeps embedded relation-schema records, as document state beside the header. `iter_records` and `export` give
  them back, so a container that embeds its schema round-trips through `compare_containers`. They take no version
  and `get` does not find them.
- Beyond V001 and D018, it refuses what it cannot index: a record that is not an entity or hyperedge object with a
  string id is C010, and an unknown header `content` is C002.
- A history container needs `history_export` in both modes. The container needs the flag, not a record, so nothing
  is skipped instead.
- D018 also covers an id whose loaded versions do not increase, in number or time, or collide with versions the
  store holds, and a version after a history header's `as_at`. Missing store fields default to the next version,
  the load time and `recorded_by: "load"`.
- `header=` replaces the container's or the stream's header. A `str` or path is read: `.jsonl` through `iter_jsonl`,
  else `read_container`. `LoadReport.records` counts the ids this call loaded; the prototype counted every id in the
  store. A load is a write, so the clock ticks after it.

### Reads and export

- `find_by_key` is `StoreBase`'s: `find` with the key bindings as the pattern, then key digest equality.
  - The key roles compare as a set, so a multi-valued key role takes several patterns; the prototype compared sorted
    role lists.
  - Positions in the patterns take part.
  - A special or unbound key value names no key group, so the result is [].
  - An `any` value is `ValueError`.
- `supersession_walk` is `StoreBase`'s: `find` on `khg:supersedes` with the record kind `lifecycle`, every rank and
  visibility, at `as_at`. It is breadth first, in id order, as the prototype.
- An undeclared relation in `find`, `incident` or `export(relations=...)` is S001; the prototype returned [].
  `limit=0` returns []. Malformed patterns are `ValueError`, and malformed values in them give their C codes.
- `export(relations=...)` exports the closed slice (`hif.select_slice`) in the khg formats as well; the prototype
  sliced HIF only. A HIF history export is `ValueError`. The computed header's `complete` follows the D002 rule over
  entity and fact values; the prototype checked entities only. Exported records have no `derived` block (the
  prototype).

### Clocks, `Where`, `Timed`, `compare_containers`

- `MemoryStore(schema)` defaults to `SystemClock` (the P7 and P10 sequences). `SystemClock.set` pins the clock
  forward only. `ScenarioClock` accepts a fractional step.
- Timestamps are written without a fraction on a whole second, else with up to six digits, trailing zeros dropped.
  A write without `at` whose clock is not after the store's latest is placed 1 microsecond after it.
- `Where` checks its sets against the vocabularies (`ValueError`; a bare string is `TypeError`), and `as_of` and
  `as_at` against their grammars (C011). It accepts any iterable. `Where.of` takes a mapping, as the scenario files
  write it. `DEFAULT_WHERE` is the default argument, to satisfy flake8-bugbear.
- `Timed.calls` holds `{method, args, ns, size, error?}`. The args digest binds the call to the protocol signature,
  with defaults filled, so a positional and a keyword call give one digest. An iterator argument enters as
  `{"$iterable": type}` and is never consumed; `iter_records` is consumed inside the timing.
- `compare_containers` returns `{path, a, b}` per header field and `{path, id, version?, fields?, a, b}` per record,
  in order. Records are keyed by (id, version) when either header says `content: history`.

### The conformance runner

- **Outcomes.** A scenario is inapplicable only when its `requires` holds a flag the store does not declare in
  `info()`, or that `capabilities=` leaves out (the ruling). It fails when a clause does not hold, a call raises
  what the step did not expect, or the store raises `CapabilityMissing` for a flag it declares. It is `cantTell` when
  the store raises `CapabilityMissing` for an undeclared flag the scenario does not list, or asks for a projection,
  clause, operation or argument this runner does not know. The prototype called the first case inapplicable, with a
  note.
- `capabilities=` intersects the store's declared flags; `only=` takes globs. The factory is called once to read the
  declared flags, then once per applicable scenario.
- `hif_valid` runs `validate_hif` (J V H R P, then decoding, C, S and D), which is stricter than the prototype's
  vendored schema plus decoding. Files named by scenarios resolve in `data/fixture/`.
- A step's `at` is passed to the write, as in the prototype. `@fixture[core]` is computed from the data flags, and a
  test pins it to the index's four ids.
- **The report** is JSON with an `@context` that maps the keys to EARL and Dublin Core terms. It has an `assertor`, a
  `subject` (the store's id, interface version, declared and tested flags, contracts), the `suite`, the `summary`
  and one `Assertion` per scenario under `@graph`. Each result has an `outcome`, an `info` and, when inapplicable, the
  `missing` flags. It carries no dates, so it is deterministic. `write_report` writes it atomically.

## Deviations from DESIGN.md

None in the interfaces: every §6.1 signature, the §6.2 semantics and the §6.3 names are as written. The decisions
above fill gaps, or follow §6.3's table where the prototype was looser (temporal keys and read flags). The additions
beyond §6 are:

- `Where.of`, `Where.as_dict` and `DEFAULT_WHERE`;
- `StoreBase.need` and its context manager;
- `conformance.write_report`, `run_scenario` and `run_suite`;
- `store.data_flags` and `FLAGS`;
- the `violations` key of a `KeyCollision` raised without an incoming fact.

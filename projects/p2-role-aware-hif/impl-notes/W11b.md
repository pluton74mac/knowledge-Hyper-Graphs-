# W11b: `scorers/`

Step W11b of the [Implementation plan](../DESIGN.md#implementation-plan): the C5 scorers of DESIGN §9, except the
memory gold of §9.5 and the memory scorer, which step W11a builds (`scorers/memory.py` is a stub that W11a owns).
It starts from `khg_c5_proto.py` (equal-mass bins, bootstrap, `binding_coverage@k`) and takes its expected values from
`research/probes/scorers/c5_reference_cases.py`. Where DESIGN.md was ambiguous or silent, the decisions below follow
R05 (`research/05-prior-art-scorers.md`), the design examples and the prototype. Nothing in DESIGN.md,
`design-examples/` or `research/` was edited, and no file of another step was changed.

**Superseded in the review round (2026-09-24).** Group f's fixes (`review-fix-f.md`) change these statements
below; the code and its docstrings are current:
- **Extraction, "Alignment (E-M3)".** The weight is w = M·ν + β with M = 1 + min(Σ|B_p|, Σ|B_g|), so the alignment is
  lexicographic over the document: largest Σν, then largest Σβ, then the id tie-break. (N+1)·ν + β ordered only
  within one pair (f-scorers-01).
- **Extraction, entity values.** Gold follows `redirect_to` through the gold documents' records only; a prediction
  through its own queue item's records first, then the gold's (f-scorers-04; extraction and stability alike).
- **Retrieval, "Answers".** Against a text-only gold, a missing, abstaining or text-less response scores 0, so the
  answer metrics average every answerable question; the budget curve's denominator is every answerable question
  (f-scorers-02, -03).
- **Completion, "Ranks".** A `model_rank` outside its tie block is C010 (f-scorers-05).
- **Inputs, extraction outputs.** Queue payloads and bare hyperedges pass layer C first (so a bare hyperedge's
  extracted evidence needs `doc_sha256`, `selectors` and `activity`, C007), and a goal is C010 (f-scorers-08, X-03).

## Decisions

### API extensions (keyword-only; every §9.2 and §1.3 call works unchanged)

- **`rank_stats(..., filter="exact")`.** A `completion-rank` record carries one set of counts and the c5-io schema is
  closed, yet `CompletionConfig.filter` says the other two filters "are always reported beside it". So
  `rank_stats` takes the filter, and `score` accepts `outputs` either as records (computed with the headline
  filter) or as `{filter: records}`. `breakdowns["filters"]` reports all three, with `null` for a filter whose
  records were not given.
- **`FilterIndex.from_records(*splits, schema=None, slots=("core", "qualifier"), manifest=None)`.** The exact
  filter compares the core and qualifier bindings, which needs the schema to tell them from time and meta bindings.
  The §1.3 call has no schema, so without one every binding takes part (the full-tuple filter, using the query
  fact's own bindings when it is indexed) and `monotone` and `time_aware` raise `ValueError`. P3b should pass
  `schema=` for relations with a time model. `manifest` reads a `c4-split-manifest` (§9.6: "which `FilterIndex`
  reads"); splits are otherwise named train, valid and test by position.
- **`completion.score(..., schema=None, index=None)`.** The `stare` preset needs the relations' `primary` to pick
  the subject and object queries (`ValueError` without a schema). C-M7 counts a top-1 as correct when it is any
  known answer; only the index knows them, so without `index` the top-1 must be the target and the report lists
  `approximated: ["top1_known_answers"]`.
- **`build_queries(..., qset="khg-completion", split="test")`.** `qset` and `split` are required fields of a C4
  item. The result is a `QuerySet`, a `list` whose `excluded` counts the left-out targets (`literal`, `special`), as
  §9.2 asks ("excluded literal targets are counted").

### Report shape and stamps

- Every `score()` returns exactly `{scorer, config, contracts, aggregate, breakdowns, items, bootstrap}`. The stamps
  of §9.1 go into `config`: `qset` (the sorted question sets read), `schema` (`{id, version, sha256}` of the schema
  argument, else of a `c4-header` among the items) and, for completion, `effective` (the filter and rank after a
  preset). `contracts` is `CONTRACTS`. No scorer renders text, so no `khg-render/1` stamp appears.
- Scores are computed with `Fraction` and written as floats (the nearest double), so 25/48, 13/100 and 393/2000
  come out exactly. Means of floats use `math.fsum`. Nothing depends on set or hash order: `test_determinism.py`
  runs four scorers under three `PYTHONHASHSEED` values and compares the reports byte for byte.
- `bootstrap` is `null` when `resamples` is 0 and for stability (which has no configuration for it; its dispersion
  is across runs).

### Inputs

- **C4 items** run the draft schema (`khg-c4-items-0.1.0`): I001, I002 and I004. A finding in an embedded C1 value or
  record (a `khg-record` code) becomes I003 with the original finding under `nested`, as §8.1 states for the c4
  pipeline. S findings met while a scorer reads an embedded gold record (an undeclared role, MC178's fault) are
  re-raised the same way. I005 (the memory-gold replay) is W11a's. Items of other C4 kinds are skipped, so a whole
  C4 file can be passed; duplicate `doc_id`s or `qid`s are I002.
- **System outputs** run `khg-c5-io-1.0.0`; a record of another `kind`, or two records for one qid, is C010 (the
  schema's own code). A non-object line is J007.
- **Extraction outputs** are C3 queue items (`run.run_id`, `run.order_id`, `doc.doc_id`, `payload`; Q001 without
  them, Q003 for another kind) or bare C1 hyperedges. A bare hyperedge names its document through the
  `source.doc_id` of its evidence (extracted evidence first; exactly one document, else C010) and forms the unit
  `(null, null)`. Every item passed is scored whatever its folded queue state; callers filter by state.
- The schema argument goes through `load_schema` (a `Schema`, a document or a path).
- The input checks use their own closed-resolver jsonschema runner over the packaged schemas. When W11a lands
  `validate.validate_item`, `_inputs.check_items` can delegate to it (a minimal change W11a may make).

### Extraction

- A fact's bindings are its content bindings (core, qualifier, time), with role, position and value; meta bindings
  never count. Entity values follow `redirect_to` over the entity records of the gold documents and the queue
  items.
- **Dedup** is by `content_key` per (run, document), keeping the smallest id (qid for queue items), so the result does
  not depend on input order. Gold is deduplicated the same way and reported apart.
- **Strict (E-M1)** is a 1:1 matching (the Hungarian solver on 0/1 weights) under the literal rule; with
  `literal_match="exact"` it is `content_key` equality.
- **Core (E-M2)** applies E-M1 to the distinct cores. DESIGN calls it "`core_key` equality"; the literal rule applies to
  core literals too, so it is exactly `core_key` equality under `exact`, and a core literal that refines the gold
  matches under `truncate_to_gold` (otherwise core could be stricter than strict). With `core_roles="key"` a
  relation without a key uses its core slot.
- **Alignment (E-M3):** N is the largest binding count of the document's facts, so w = (N+1)·ν + β orders by ν, then β.
  Weights are 0 across relations. The solver's tie rule: row by row in id order, each prediction takes the first
  gold (by id) it can take in some maximum-weight alignment; an unaligned prediction ranks after every alignment.
  ν and β are maximum matchings under the literal rule (value only for ν; role and position too for β).
- **Pooled (E-M7)** elements are (relation, role, position, value); **pairwise (E-M8)** elements are unordered pairs of
  a fact's bindings, matched in either pairing; **participant sets (E-M9)** compare value multisets. All are sets per
  document, matched 1:1 under the literal rule.
- **Runs.** Every run `(run_id, order_id)` is scored against every gold document; the aggregate is micro over
  (run, document) units, so the P/R blocks count each gold fact once per run, while `aggregate["n_gold"]` counts it
  once.
  `breakdowns["by_run"]` and `run_dispersion` (mean, sd, min, max over runs) give S-M6. Predictions for documents
  without gold are not scored and are counted (`n_pred_unscored`, `unscored_docs`).
- **Per arity (E-M10).** A matched or aligned pair counts for precision in the predicted fact's bin and for recall in
  the gold fact's bin, on `arity` and `model_arity`; `aligned_arity_pairs` lists the (predicted, gold) arities. Macro
  averages take P over bins (or relations) with predictions, R over those with gold, and F1 over all present.
- **`model_arity`** counts the core and qualifier bindings whose value is not a literal (the formula of `build_c4.py`,
  which gives the C4 example's 3 for `f:king-14`).
- **Ign (E-M11)** drops gold facts and predictions whose C1 `core_key` is in `seen` and recomputes E-M1 to E-M6.
- **Presets** add `aggregate["preset"]` and leave the C5 metrics unchanged. Both reproduce their counting: nested
  loops over the undeduplicated lists (so R can exceed 1, R05 E6) and exact literals. `hyperred_quintuplet` emits one
  `(relation, subject, object, role, position, value)` per other content binding of a fact with a `primary` (a
  triple when there is none); `text2nkg` merges predicted facts that share (relation, subject, object), as its
  `compaction` does, and compares whole facts. Relations without `primary` are counted as unmapped.
  `approximated` names the difference: `entity_bounds` (ids stand for spans) and `serialisation_order` (C1's
  canonical form makes Text2NKG's order-sensitive strings irrelevant).
- The R05 table's `binding_greedy` (E8) is not a C5 metric; the test recomputes greedy by hand to show 1/2 against
  the Hungarian 2/3.

### Stability

- A unit's set holds `(doc_id, key)` for its items, so the same fact from two documents is two elements.
- Δ_order always reads the (run_id, order_id) sub-units, also with `unit="run_id"`, where the other metrics use the
  pooled runs.
- A run with no queue items at all cannot be seen (queue items are the input); per-document results show empty
  runs (J = 1, counted in `n_empty_pairs`, R05 S2). `per_document_mean_jaccard` averages the documents with output.
- S-M5 matches gold by the key (exact identity), not by the extraction literal rule.

### Completion

- **Candidates** are ids: entity and fact ids, and the `_:lit:` id of a literal (as `project.positional` writes it);
  special values are never targets or known answers.
- **Queries** (`build_queries`): one per core or qualifier binding in `slots`, in fact-id and canonical binding order,
  for every hyperedge that is not a goal or a lifecycle record. The context is the fact's other bindings in `slots`
  (the C4 example's form: time bindings are left out). The ids are `cq:<fact id>#<bid>` and `c4:cq:<fact id>#<bid>`
  (a SHA-256 hex form beyond 512 characters). The fixture's `king-14` holder query equals the C4 example in every
  field but its ids and qset.
- **Universes.** `entities_of_type` lists the usage's entity filler types. `seen_in_position` lists the entities seen
  among `facts` in the target's position: for a `primary` subject or object role, every entity seen as a subject or
  object (StarE's WD50K universe), else the entities seen in that role. Fact targets list the facts of the admitted
  relations, literal targets the literals seen in the role.
- **Known facts** are the indexed facts with status `asserted` or `disputed` (a superseded or retracted fact is known
  to be wrong). Facts in other statuses are kept only to be looked up by id (a query fact's validity for
  `time_aware`); goals and lifecycle records (the reserved `khg:` relations) are never indexed.
- **Filters.** `exact` compares the context with each known fact minus one binding of the target role, as multisets of
  (role, position, value identity), so an ordered target's position is implied by the gap. `monotone` is
  `record.fact_refines(g, f[ρ←c])` with the target at g's position (a test checks it against brute force on every
  fixture query). `time_aware` keeps the exact matches whose definite validity overlaps the query fact's (the bound
  table; a query without an as-of instant takes its fact's validity as the query time, as temporal link prediction
  does); an undated query fact filters nothing, and facts of invariant or timeless relations always overlap.
- **Ranks.** `tie_exact` is exact for tie blocks up to 64; larger blocks use floats (the harmonic expansion beyond
  100). `model` without `model_rank` falls back to pessimistic (`approximated: ["sort_order_ties"]`). A record whose
  `n_greater + n_equal + 1` exceeds the unfiltered candidates is C010.
- **Averages.** Per task, per fact, and macro over arity bins of the per-fact means, on `arity` and `model_arity`;
  a query without a record scores RR and Hits 0 and is left out of MR (`n_missing`). The headline is `macro_arity`,
  `per_task` with `hype` or `hyper`, and the subject/object mean with `stare` (R05 §3.4). The optional C-M6 adjusted
  Hits@k and AMRI and the rank audit are reported too.
- **Presets** override `filter` (exact) and `rank` (pessimistic; the model's order for `stare`). `stare` keeps only
  the subject and object queries and averages the two positions; it always reports `qualifier_order`.
- **Calibration.** Over the queries whose record has `top1`; confidences are read by their shortest decimal form
  (0.95 is 19/20), so bin edges are exact. Per arity bin, fewer than `min_bin_queries` queries give counts only
  (`suppressed`).

### Retrieval

- Units are read in `rank` order (input order among equal ranks); hyperedges(L[:k]) is the union of the top-k units'
  `hyperedge_ids`. The reported cut-offs are `ks` plus `headline_k`.
- **nDCG** uses binary relevance with a support hyperedge counted at its first unit only, so duplicates or pair units
  of one hyperedge never push it above 1; R1 gives 0.650921 and 0.75.
- **`binding_coverage@k`** counts (hyperedge, bid) pairs: a unit's `bids`, or every binding of a `hyperedge` unit
  without `bids`; other units without `bids` cover nothing. It is computed when `facts` holds hyperedges (a support
  hyperedge missing from it is a `ValueError`), over all of a gold hyperedge's bindings (the scorer has no schema).
  `facts` may be a mapping or an iterable of C1 records; its entity records resolve redirects in answers.
- **Answers.** Single mode reads the first answer value (value identity, after redirects); the headline `em` is the
  value EM when the gold has values, else the text EM. Set mode gives set P/R/F1 with the empty-set flags. For the
  joint scores, answer P and R are the set P/R, the value EM, or the token P/R when the gold has no values (R05 R5).
  Answer metrics average the answerable questions; ranking metrics the questions with support.
- **Abstention** precision and recall count abstaining responses on unanswerable questions; a missing response
  neither abstains nor answers.
- **Cost.** Median is the usual median (the mean of the two middle values for an even count); p90 and p95 are nearest
  rank (R05 R7). **The budget curve** (critique CONS-07, which DESIGN names without a formula): the questions in
  input order each spend their prompt and completion tokens; at ten budgets (tenths of the total) it reports the
  answer EM reached by the questions that fit, over all answerable questions.
- KILT recall (R05 R1, R2) is left to the adapters (R05 D-C5-12); the tests check it only against the probe.

# W5: lifecycle, keys, the container D checks and `identity`

Step W5 of the [Implementation plan](../DESIGN.md#implementation-plan): the lifecycle transitions and the four axes,
the key invariant judged per instant on definite windows, the `KeyCollision` info with its §2.5 action table, L008,
the cross-record D checks in `validate/layers/d_container.py`, and the non-normative `identity.relate`. It ports
`khg_synth.py` (keys, collisions, `relate`), `khg_store_proto._version_rule` and `_check_d011`/`_check_d012`, and
`khg_validate_proto._d_container`, `_d_graph`, `_d_history` and `_q_d`. Where DESIGN.md was ambiguous, the decisions
below follow `design-examples/` and the prototypes; three deliberate departures from the prototype are listed under
"Deviations". Nothing in DESIGN.md, `design-examples/` or `research/` was edited.

## Decisions

### API shape

- **Problems, not exceptions.** Each lifecycle rule returns `Problem(code, id, pointer, message, version)`: the
  validator turns them into findings (`/records/<i>` + `pointer`), and a store raises `error_for(problems)`:
  `VersionError` for D011-D014 and D018 (§6.1), `ValidationError` for the others (D008, D010), with
  `info["problems"]` (and `info["findings"]` on a `ValidationError`).
- **Argument order** follows W3: records first, schema after (`version_problems(old, new, schema)`,
  `collisions(state, batch, schema, *, post=None, disputed_rule=True)`, `l008_warnings(records, schema, *,
  ids=None)`). Record collections are `{id: record}` or any iterable of records. A schema is a `Schema` or a
  document used unchecked, as in `record`.
- **`collisions`** is the prototype's function: `state` before the write, `batch` written, `post` the whole state
  after it when an event changes other records too, `disputed_rule` for a `put` (events pass False, as the
  prototype store does). It only looks at the key groups of the batch, so `state`/`post` may be restricted to them
  (a store's key index).
- **`key_invariant_violations`** returns `Violation(relation, key_digest, temporal, ids, at)`: the sorted ids of a
  set of facts that hold together and the first instant where they do (for the D016 message). `keys=` restricts it
  to some groups.
- **`relate`** lives in `identity/classifier.py` (not `identity/relate.py`, which would shadow the function with
  the module).
- **`parse_timestamp`** (in `lifecycle`) reads the RFC 3339 UTC timestamps of `recorded_at` and `as_at`, fractions
  included (the record schema's `timestamp` pattern), as integer microseconds; C011 otherwise. W3 had only the
  instant grammar, which has no fractions.

### Layer D

- **Order and paths.** D009 (`/header/schema`); per record D001, D007, D017 and D015 (`/records/<i>`,
  `.../status`, `.../derived`); history rules (`.../recorded_at`, `.../status`, the binding or evidence path);
  D002 and D020 at the binding value; then D008, D010, D011, D012, D016 and L008 at the record of the id at fault
  (D016 and L008 at the first id of the group or pair). Messages name the ids; the prototype put ids into paths.
- **Latest versions.** D002, D020, D008, D010-D012, D016 and L008 read the current version of each id (layer S's
  `latest_records`; the `entities` and `facts` S leaves in `ctx.state` when it ran). D015 and D017 read every
  record, history versions included.
- **D001 and D009 run here too**, as the stub's docstring (W4) listed: MC133 records D001 beside D007 and D002, and
  MC134 is the container pin. D009 compares id, version and sha256; in a HIF run decoding owns the pin (W6), so
  `d_container` does not repeat it on the decoded header. A queue header's pin (the prototype's `_q_d`) is here as
  well; W9's layer Q should not duplicate it.
- **Without a schema** the container rules are skipped (the prototype returned nothing), after D009 has been
  reported once by whichever step asked first. A single record still gets D017 without a schema.
- **Robustness.** What cannot be read (a malformed value, an unknown relation or role) is left to C and S: facts
  whose key digest or bounds cannot be computed are left out of the key checks, and every rule reads broken
  structure without raising. `skipped == []` holds on the 180 cases and on the test battery.
- **What each case reports.** All 22 container D cases give exactly the codes the list records at the first
  rejecting step, under both engines (a stronger check than the G2 rule, as W4 did for C, V and S).

### Semantics

- **The transition table** is §2.7's nine rows (`TABLE`); `TRANSITIONS` is its twelve (from, to) pairs for existing
  facts, the prototype's set. A lifecycle record may only go from asserted to retracted, and not a `khg:retracts`
  record ("cannot themselves be retracted").
- **History containers** check D014 on consecutive versions only (the registry's wording); a first version's status
  is not judged. A status change runs the version rule on the two versions read as asserted, without `status_ref`
  and, when leaving `goal`, without the `goal` block (the prototype's reading). A `novalue` end may be replaced.
- **`with_status`** drops the `goal` block whenever a record leaves `goal`, retraction included: C012 allows the
  block only in status `goal`.
- **Adding a binding to a `complete` role is D013 even when the old version had no binding of that role**, as §2.9
  states ("add bindings only where the role is not `complete`"; ⊑ keeps a complete role's size). The prototype
  allowed it when the role was empty. No scenario or case depends on it.
- **Evidence across versions** is compared canonically with `supports` defaulting to the bids of the old version
  (§2.8.1), so an omitted `supports` equals the explicit default. The prototype defaulted it to `[]` (it
  canonicalised the evidence with no bindings), so omitting a default list counted as a rewrite. Evidence
  `recorded_at` takes part: the earlier record stays as written.
- **L008** flags every pair of one temporal key with a possible but not definite overlap, preferred facts included,
  as the prototype and the registry's wording do.
- **`relate`** is `khg_synth.relate`: a negation conflict compares the other core roles by identity and needs a
  possible overlap (DB §2.18 wrote "refine" and "definitely"); the 37 rows do not tell the two apart (C3c and X5
  are timeless).
- **`cases.json`** was generated from DB's `run_identity.py` (its `CASES`, `REL` and the three policy variants)
  with the labels of `identity-results.json`, records converted to C1 bindings and relations to
  `khg-relation-schema/1.0.0`. It adds `action`: the §2.5 action a write of the incoming fact beside the stored one
  collides with, which reproduces DB's outcome column (3a close_older, 3b dispute, X2 dispute, X4 close_incoming,
  the naive key and the policy variants). The C3a-supersede row's schema is M017 in 1.0 (supersede on a temporal
  key), so the test checks the refusal and then uses the schema unchecked; `relate` does not read the policy.

## Deviations from the prototype (DESIGN.md unchanged)

1. **The invariant is judged at every instant where a definite window starts or ends.** DESIGN §2.5 states the
   invariant per instant; the prototype checked only the instants where a window starts, which misses a preferred
   holder ending while two normal holders go on (`test_the_judgement_is_made_where_a_window_ends_too`). The result
   is a superset of the prototype's: on 3,000 random groups the prototype never found a violation that this did not.
2. **Two starts at -inf (both `novalue`) are `same_start`.** The prototype's test made the stored fact "earlier"
   (its empty start window lies "before" the other's, and vice versa), which would give `close_older` with no start
   literal to close at. §2.5 defines `same_start` as "neither start window lies before the other".
3. **A deprecated fact never collides, under the disputed-key rule too** (S-KEY-005: "never collides"): a deprecated
   incoming fact does not join a dispute, and deprecated disputed facts are not conflicts. The prototype applied the
   rule regardless of rank.

**A gap the store should close** (the prototype has it too): `collisions` reports the incoming asserted facts that
take part in a violation. A write can also break the invariant without one, for example by retracting the only
preferred fact of a key while two normal ones hold, or by a new version whose refined key literal moves a preferred
fact to another key. The store can catch these with `keys.key_invariant_violations(post, S, keys=touched)` over the
key groups the write touched (before and after) and raise D016 with those violations.

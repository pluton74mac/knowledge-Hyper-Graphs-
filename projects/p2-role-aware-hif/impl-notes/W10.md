# W10: `migrate/` and the v0 sample

Step W10 of the [Implementation plan](../DESIGN.md#implementation-plan) builds `migrate.v0_sample_to_v1`. It
migrates the knowledge base's `schemas/sample.hif.json` (single-string `attrs.role`, a weight on every edge) to
`khg-record/1.0.0`, and returns the generated relation-type schema, the C1 container and the F report (§11.3). It
ports `build_examples.migrate_sample` from `research/designs/work-synthesis/`. Where DESIGN.md was ambiguous, the
decisions below follow `design-examples/` and the synthesis prototype. Nothing in DESIGN.md, `design-examples/` or
`research/` was edited, and no file of another step was changed. The `khg-migrate` command is W12's.

The step ran twice. The first attempt was interrupted after it had written the package, the tests and these notes.
The second pass reviewed that work against DESIGN §10, §11.3 and the registry, kept it, and made the changes listed
under [Second pass](#second-pass).

## Decisions

### The call

- **Signature.** As §10.2: `v0_sample_to_v1(hif) -> (schema, container, report)`. The result is a `NamedTuple`
  `Migration(schema, container, report)`, so it unpacks as the triple of §10.2. `hif` may be a parsed document, raw
  bytes or a path, as for `from_hif`. It is read under layer J, and an unreadable path raises `OSError`, as in the
  validator.
- **`schema`** is the generated document (a dict), not a `Schema`. It is the golden `sample.relation-schema.json`,
  which `--schema-out` writes, and `load_schema(schema)` gives the `Schema`.
- **`report`** is the whole `khg-migration-report/1.0.0` document `{format, from, findings}`, which is the golden
  `sample.migration-report.json`. Its entries are `{code, edge?, message}`, as in the golden. They are not the
  `{code, severity, layer, path, message}` findings of §8.1.
- **The function and its module share a name.** §10.1 names the file `migrate/v0_sample_to_v1.py`, and §10.2 names
  the function `migrate.v0_sample_to_v1`. The package re-exports the function, so `migrate.v0_sample_to_v1` is the
  function. `import khg_contracts.migrate.v0_sample_to_v1 as m` also gives the function, because it reads the
  package attribute. `importlib.import_module("khg_contracts.migrate.v0_sample_to_v1")` (or `sys.modules`) gives the
  module. A test pins all three.
- **Additions** to the §10.2 surface, for W12 and the tests:
  - `Migration`;
  - `MIGRATIONS` (`{"v0-sample": v0_sample_to_v1}`, for `khg-migrate --from`);
  - `V0_SAMPLE` and `REPORT_FORMAT`;
  - `generate_schema` (the schema alone, unchecked);
  - `dumps` with `LAYOUT` (below).

### The stored arity: D015

§10.2 says the call raises `ValidationError` "on a stored arity that disagrees", and §11.3 says "a mismatch raises".
Neither names a code, and codes are never invented.
- **No F code fits.** The registry has no F error code. F015 is `info`: "stored arity checked against the C1 rule and
  dropped".
- **F015 raised to `error` was ruled out.** The registry's only precedent for a severity other than the registered
  one lowers it (S003 on candidates, `Registry.severity`).
- **D015 is the chosen code:** "a stored derived block disagrees with recomputation". The v0 `arity` is a stored
  derived value. Design B's §11.3 table says "dropped (derived)", and its first migration run reported exactly this
  mismatch as `MIGRATE-E01` (DB §2.7), a code the synthesis registry did not carry over.

How the refusal behaves:
- The finding sits at `/edges/<k>/attrs/arity` and names both numbers.
- Every disagreeing edge is reported, not only the first.
- A non-number, `null` or a boolean disagrees (in Python, `true == 1`).
- An integral float such as `4.0` agrees. Its F015 message says `stored arity 4.0 checked and dropped`.

### The input: refuse, never drop or guess

§11.3 pins every choice that fixes a key, for the sample's features. Anything else has no pinned reading. So the
migration refuses it, instead of dropping it silently (the prototype ignored unknown members) or guessing a rule. The
`v0-sample` format is exactly the sample's vocabulary:
- metadata: any keys;
- nodes: `{node, attrs: {type, label?}}`;
- edges: `{edge, weight?, attrs: {relation, source, arity?, valid-from?}}`;
- incidences: `{edge, node, direction?, attrs: {role}}`.

Every refusal is a `ValidationError` with registered codes and a path into the input. Each code is the registered
code whose meaning covers the fault:

| Fault | Code | Why this code |
|---|---|---|
| not JSON, not an object, not HIF 0.1 (including an extra key on a node, edge or incidence record) | J, H | layers J and H (the vendored schema), as for any HIF input |
| an id that is not a string | P002 | the profile's rule (F10); integer ids belong to 1.1's foreign import (F001, planned) |
| a node or edge id outside the C1 id grammar (white space, control characters, over 512 code points, the `_:` prefix) | C011 | node and edge ids become C1 record ids |
| an id, relation, role or type not in NFC | S020 | C1's NFC rule; silent normalisation could merge two ids (1.1 plans F014 for foreign import) |
| a node or edge declared twice; an incidence naming an undeclared edge or node | D001; D003, D002 | as decoding (§4.3) |
| an edge without incidences | S007 | its fact would have no participant |
| an incidence without one non-empty string role; an exact repeat of (edge, node, role) | R001; R002 | the convention's rules 1 and 2, whose key the sample already uses |
| any other `attrs` key, `role-position`, a node or incidence `weight` | C009 | "unknown field": §11.3 gives it no place. `role-position` would need an `ordered` usage, which no rule generates |
| a missing or mistyped `type`, `label`, `relation` or `source` | C010 | the C1 field each one becomes: `types`, `label`, `relation` and the evidence `doc_id` |
| a `valid-from` that is not `YYYY-MM-DD` (ASCII digits); a date C1 cannot hold | C004; S006 | the codes of the time literal it becomes. S006 covers February 30, year 0, and a date before 1583, which must state its calendar |
| `asc`; a directed file with an incidence without direction; an undirected file (or one without `network-type`, which HIF reads as undirected) whose incidences all have one | P007; P010; P011 | the migrated file follows the profile's direction rule, so these would change the network type |
| a metadata key that is a declaration key, `default_attrs` or `khg-*` | P008 | the same rule `to_hif` applies to `hif:metadata` |

The planned codes F011 to F014 of 1.1's foreign import name some of these faults, but they are not registered, so
they are never emitted.

**The outputs are checked too**, as a safety net:
- **The generated schema** goes through `load_schema` (V, M). A `khg:` role or type is M008, and a type or role with
  a space is M015. `start_time` used as an ordinary role in a relation with `valid-from` is M002.
- **The container** goes through `validate_container` (V, C, S, D). A node and an edge that share an id give D001
  and D007.
- **Paths.** Their findings have paths into the generated document, so the error carries that document in
  `info["schema"]` or `info["container"]`. Messages start with "the generated schema: " or "the migrated container:
  record '<id>': ".

### Beyond the sample

The sample exercises one branch of each rule. The other branches follow the rule's wording, and none of them changes
the sample's result:

- **Directions.** A usage gets a direction only when all its incidences agree (§11.3). When they disagree, each
  binding keeps its incidence's direction, as C1 allows (`direction?`), so no direction is lost. The prototype
  dropped them. The round trip through HIF keeps them.
- **Optional members.** Without `arity`, nothing is checked and there is no F015 (the prototype raised, because
  `None != arity`). Without `weight` there is no F006 and no `extensions`. Without `label` the entity has none.
- **Metadata.**
  - Every key other than `schema` and `conventions` goes to `extensions["hif:metadata"]`, in source order. The
    prototype took exactly four keys and raised when one was missing.
  - The header gets `extensions` only when a key remains, so `from_hif` gives the same header back.
  - F016 is reported only when `schema` or `conventions` was present. Its message names the keys replaced: "metadata
    schema and conventions replaced by the declaration block" for the sample.
- **`valid-from`.** The literal is `+YYYY-MM-DDT00:00:00Z` at precision 11 without a calendar, as in the prototype.
  The canonical form adds `gregorian` from 1583. An earlier date is refused (S006) rather than read as Gregorian,
  because historical sources often write Julian dates in ISO form. C1 makes the same choice.
- **Text.** Labels and the evidence `doc_id` are not ids, so the canonical form normalises them to NFC; no refusal.
- **Order.** The schema, the container and the bids do not depend on the order of nodes or incidences, nor on the
  hash seed (sets are sorted before use). The report follows the file's edge order, as in the golden.

### `dumps` and `LAYOUT`

The goldens use the prototype's `dump` layout:
- one top-level key per line;
- the arrays `entity_types`, `roles`, `relations`, `records`, `nodes`, `edges` and `incidences` one record per line,
  with `", "` and `": "` separators and non-ASCII text kept;
- the report as `indent=1` JSON.

`migrate.dumps(doc, compact=migrate.LAYOUT[name])` writes each golden byte for byte, so `khg-migrate` can reproduce
the committed files. The layout is only a presentation: canonical JSON is what digests and comparisons use.
`record.write_container` writes the canonical layout instead, with the same content (a test checks both layouts).

### Test data

The v0 input is a verbatim copy in `tests/migrate/`, and a test compares it with `schemas/sample.hif.json` when the
checkout has the file. `tests/loaders/r03-cases/c00-kb-sample.hif.json` (W7) is a third copy with the same sha256.
The children spawned by the hash-seed tests block sockets themselves, as `tests/gate/g1_chain.py` does. That helper
runs the fixture only, so the migrated sample has its own child script.

## Deviations from DESIGN.md

1. **The goldens are not committed next to `schemas/sample.hif.json`.** §11.3 says "W10 commits them [the four
   goldens] next to `schemas/sample.hif.json`", but `schemas/` lies outside W10's files
   (`src/khg_contracts/migrate/**`, `tests/migrate/**`). The goldens are in `data/sample/` and `design-examples/`.
   - `test_goldens_committed_next_to_the_sample_equal_the_packaged_ones` skips until they are copied, then checks
     them byte for byte.
   - To copy them: `cp src/khg_contracts/data/sample/sample.*.json schemas/`. Alternatively, `khg-migrate` (W12) with
     `dumps` can regenerate them.
2. **The arity refusal carries D015** (see above). DESIGN names no code for it.
3. **More refusals than §10.2 lists.** §10.2 names only the arity. The input and output checks above refuse what the
   pinned rules cannot migrate, each with a registered code.
4. **The API adds** `Migration`, `MIGRATIONS`, `V0_SAMPLE`, `REPORT_FORMAT`, `generate_schema`, `dumps` and `LAYOUT`
   to §10.2's `v0_sample_to_v1`.
5. **Bindings keep their direction when a role's incidences disagree.** §11.3 is silent on this, and the sample does
   not exercise it.

## Second pass

The review of the interrupted attempt covered the following:
- **Spec.** Each row of the §11.3 table against the code.
- **Codes.** Every code the migration emits against `error-codes.json`: registered, active, and its meaning. F011 to
  F014 are planned and never emitted.
- **Cross-module rules.** The P008 rule against `to_hif`, and the C011 grammar against the record schema's
  `definitions/id`.
- **Edge cases.** Types (arrays, objects, floats, `null` and booleans as ids), extra record keys, `.jsonl` paths, an
  absent `network-type`, and NFD labels.
- **Verification.** The fuzzing above, the Python 3.10 and 3.13 runs, and lint and types.

No defect was found in the migration. The changes:
- **G1 assertion 7.** The G1 chain on the migrated sample now runs five hash-seed children (`PYTHONHASHSEED` 0 to 3
  and unset), as §1.2 asks, instead of three. It also checks that the chain's first HIF digest is the golden's. The
  migration-only hash-seed test uses the same five seeds.
- **Container I/O.** A new test writes the migrated container with `record.write_container`, in both the `.khg.json`
  and `.khg.jsonl` layouts, and reads it back with `read_container`. The content equals the golden; only the layout
  differs. This is the path `khg-migrate` (W12) takes.
- **The import trap.** The package docstring and `test_the_api_names` now state that
  `import khg_contracts.migrate.v0_sample_to_v1 as m` gives the function, not the module.
- **These notes.** The counts are updated (119 items; 106 pass and 13 skip without the libraries), and the fuzzing
  was rerun with 4,000 mutations.

## Observations (no change made)

- `khg-migration-report/1.0.0` is a format id that neither §11.1 nor `khg_contracts.CONTRACTS` (W0) lists.
- The report entries `{code, edge?, message}` differ from the §8.1 finding shape. The golden fixes them, and the
  registry rule says messages are not part of the contract.
- A `.jsonl` path is parsed as JSONL by layer J, as in the validator, so a v0 file with that suffix is refused (H009).
- **The full suite, last run: 6 failed, 3498 passed, 5 skipped, 5 xfailed.** None of the failures is in W10's files.
  All 6 come from W9's work in progress, which runs in parallel and changed files during this step.
  - The new `data/schemas/khg-queue-1.0.0.schema.json` is not yet in the schema tables of
    `tests/validate/test_engines.py`. This causes 4 failures.
  - `tests/validate/test_s_layer.py` has 2 queue-payload tests that now meet W9's new Q checks (Q010, Q011, Q012).
  - An earlier run of this step had 2 other failures in `tests/packaging/test_package_data.py`: the new schema was
    not yet in `manifest.json`. W9 has since fixed that. In a copy of the tree without W9's untracked paths at that
    time, `tests/packaging`, `tests/validate/test_engines.py` and `tests/migrate` passed: 371 passed, 4 skipped.
- The orchestrator's checkpoint commit `388c594` ("P2 S6 checkpoint") snapshotted the interrupted attempt's files. The
  second-pass changes are uncommitted, for the S6 integrator.

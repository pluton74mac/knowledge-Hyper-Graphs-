# W12: the four console scripts

Step W12 of the [Implementation plan](../DESIGN.md#implementation-plan) builds the four v1 commands of DESIGN
§10.4: `khg-validate`, `khg-convert`, `khg-migrate` and `khg-conformance`. They replace the W0 placeholders in
`src/khg_contracts/cli.py`, under the entry points already declared in `pyproject.toml`
(`khg_contracts.cli:validate_main`, `convert_main`, `migrate_main`, `conformance_main`). The commands are thin:
each parses its arguments with argparse, calls the library (`validate.run`, `hif.to_hif` and `from_hif`,
`record.serialize`, `migrate.MIGRATIONS`, `store.conformance.run`) and maps the outcome to an exit status. No
prototype has a CLI, so nothing was ported. Nothing in DESIGN.md, `design-examples/` or `research/` was edited, and
no file of another step was changed.

The runs that matter for the release:
- `khg-validate fixture.c1.json --kind container --schema fixture.relation-schema.json` (the CI `wheel` job) exits 0
  and prints the two designed warnings, S024 and L008.
- `khg-conformance --factory khg_contracts.store:memory_factory` exits 0 with 114 passed. Its report equals
  `conformance.to_json(conformance.run(memory_factory))` byte for byte.
- `khg-convert fixture.c1.json fixture.hif.json --to hif --schema fixture.relation-schema.json` writes the packaged
  `fixture.hif.json` byte for byte. With `--relations` set to the slice's nine relations it writes
  `fixture.directed-slice.hif.json`, and `--to khg-jsonl` from the HIF file writes `fixture.c1.jsonl`.
- The §11.3 command `khg-migrate schemas/sample.hif.json sample.khg.json --from v0-sample --schema-out
  sample.relation-schema.json --report sample.migration-report.json` writes three goldens byte for byte.
  `khg-convert sample.khg.json sample.khg.hif.json --to hif --schema sample.relation-schema.json` writes the fourth.

## Decisions

§10.4 fixes the commands, their arguments and outputs, and the meaning of the three statuses. The rest was open.

### Exit statuses

**1 means the input fails.** This covers:
- an error finding in the `validate()` result;
- IN failing validation;
- a `ValidationError` from a conversion or a migration;
- a `failed` or `cantTell` scenario;
- a store whose factory or `info()` raises before any scenario runs. The runner already reports a factory that
  raises inside a scenario as `failed`.

**2 means the command could not do its job:**
- argparse errors;
- conflicting options;
- a `--relations` id that the schema does not declare;
- an unknown capability flag;
- an `--only` glob that matches no scenario;
- a factory that cannot be imported, found or called;
- any `OSError` reading or writing a file;
- **argument files that cannot be used:** `--schema` fails layer J, V or M; `--base` is not a container; `--doc-texts`
  is not JSON. The input was never checked. This follows the validator, which raises on bad arguments and never
  reports them as findings on the input (W4.md, "Arguments are not input").

**cantTell is a failure.** This is the director's ruling as the orchestrator passed it to this step: exit 1 when any
scenario is `failed` or `cantTell`, while `passed` and `inapplicable` are not failures. §10.4 names only `failed`,
and W8.md and integration-S5.md left `cantTell` open. It matches ruling 1 of §14: a store passes when no applicable
scenario fails, and a `cantTell` scenario did not show that it passes.

### `khg-validate`

- The command calls `validate.run` rather than `validate`, so that the text verdict can name the kind that auto
  detection found. `--json` prints `report.result()`, which is exactly what `validate()` returns (a test checks the
  equality).
- The argument files are loaded before the run: `load_schema`, `jsonio.load` and `record.read_container`. So their
  failures carry the option's name.
- `--base P …` takes one or more paths and may repeat (`nargs="+"`, `action="extend"`).

### `khg-convert`

- **IN is validated first**, through the full pipeline of its kind: J V C S D for a container, J V H R P D C S for a
  HIF file. This is our reading of "Exit 1 on a validation failure". `to_hif` and `from_hif` alone check less:
  `to_hif` would copy a bad `status` into `khg-status`. On failure the findings go to stderr and nothing is written.
  The input's warnings go to stderr too.
- **Which input.** The kind is told as `khg-validate` tells it. A file declaring the role convention without the
  profile is validated as `hif`, which gives P001, since foreign import comes in 1.1 (§4.3). Any other kind (a
  schema, a record, a queue, C4 items) is exit 1 with a message. Both C1 forms and HIF files are accepted for every
  `--to`. So besides C1 ↔ HIF, the command re-serialises a container (`.khg.json` ↔ `.khg.jsonl`) and re-encodes
  or slices a HIF file.
- **The schema** is `--schema`, else the one IN embeds: a container's `relation-schema` record, or a HIF file's
  `khg-schema-document`. It is resolved by `validate.context.Context.relation_schema`, as the validator and
  `from_hif` resolve it.
- **Option checks.**
  - `--relations`, `--literal-nodes` and `--schema-document` apply only with `--to hif`.
  - `--relations` must list declared relations (`Schema.has_relation`).
  - OUT's name must fit `--to`: `.jsonl` exactly for `khg-jsonl`. `record.read_container` and the validator read a
    `.jsonl` name line by line, so any other pairing writes a file that the package misreads.
- **HIF text** is `migrate.dumps(doc, compact=LAYOUT["hif"])`. That is the layout of every packaged HIF file: one
  top-level key per line and one node, edge or incidence per line. With it the command reproduces
  `fixture.hif.json`, the directed slice and `sample.khg.hif.json` byte for byte. Nested values that `to_hif`
  copies (literals, evidence, extensions) keep IN's key order. So a canonical container, whose keys are sorted,
  gives other bytes with the same canonical form. The layout is presentation: digests and comparisons use
  canonical JSON (F10).
- **Containers** are written as `record.write_container` writes them: `record.check_container` (V and C), then
  `record.serialize`. The CLI's own atomic writer does the writing (see *Files*).

### `khg-migrate`

- The migration is `migrate.MIGRATIONS[--from]`, whose keys give the argparse choices (W10.md).
- **The layout of the goldens.** OUT, `--schema-out` and `--report` use `migrate.dumps` with `LAYOUT`. §11.3 names
  the command that produces the goldens, and with this layout it produces them byte for byte. An OUT ending in
  `.jsonl` gets the canonical JSONL container instead.
- Without `--report`, the report goes to stdout: the same text as the golden's layout. `khg-conformance` does the
  same with its report. Without `--schema-out`, the schema is not written. OUT's header pins it by id, version and
  sha256.
- The report is printed only after every file is written, so a write failure leaves stdout empty.

### `khg-conformance`

- The call is `conformance.run(factory, only=…, capabilities=…)`, as W8.md suggests.
- **`--only`** may repeat. Several globs select the union, which `conformance.run` accepts. A single glob is passed
  as a string, so the report's `suite.only` keeps the form `run` gives it.
- **`--capabilities`** takes comma-separated flags, trimmed. An empty value means no flag (the no-flag run of §6.4:
  12 applicable).
- **`--factory MODULE:CALLABLE`.** CALLABLE may be dotted (`pkg.mod:Class.factory`). The current directory is not
  added to `sys.path`: MODULE must be importable, as for any installed backend. `python -m khg_contracts.cli
  conformance` imports from the current directory, as `-m` always does.
- **The report** is `conformance.to_json(report)`. With `--report` it is written by the CLI's writer instead of
  `conformance.write_report`, for the permissions (below). The content is the same, and a test compares it byte for
  byte with the library's.

### Files, streams and `python -m`

- **Output files** are UTF-8 with `\n` line ends and replace their target atomically. The temporary file is created
  with `open(..., "x")` in OUT's directory. So the result gets the permissions the umask allows (usually 0644), as
  shell redirection would give. Nothing is left behind when a write or the rename fails.
- **Streams.** Results go to stdout; diagnostics, warnings and `wrote` lines go to stderr, prefixed by the program
  name. When stdout cannot encode a character, text lines are backslash-escaped and JSON falls back to `\u`
  escapes, which is still the same JSON.
- **`python -m khg_contracts.cli COMMAND [ARGS]`** runs `khg-COMMAND` without the console scripts (`main`,
  `COMMANDS`). The argparse `prog` stays `khg-COMMAND`.
- **Imports.** The module imports only the standard library and `errors` at import time. Each command imports what
  it needs when it runs, so import hygiene holds (`tests/packaging/test_import_hygiene.py` imports `cli`).

## Deviations from DESIGN.md

No name, argument, output or exit-status meaning of §10.4 changed. These choices go beyond it:
1. **cantTell exits 1.** This is the orchestrator's ruling; §10.4 names only `failed` (see *Exit statuses*).
2. **Argument files that fail validation exit 2,** not 1 (see *Exit statuses*).
3. **`khg-convert` validates IN first,** accepts both C1 forms and HIF for every `--to`, and refuses an OUT name that
   does not fit `--to`. It also refuses the HIF-only options with another target, and relations that the schema
   does not declare.
4. **`--only` may repeat** and `--base` takes several paths per occurrence. Both are supersets of §10.4's
   `[--only GLOB]` and `[--base P …]`.
5. **Additions** to the §10.2 surface: `cli.main` and `cli.COMMANDS` (for `python -m khg_contracts.cli`).
6. **Report writing.** `khg-conformance --report` writes `conformance.to_json(report)` through the CLI's writer,
   not `conformance.write_report`. The bytes are the same.

## Observations (no change made)

- `record.write_container` and `store.conformance.write_report` (W3, W8) create their temporary file with
  `tempfile.mkstemp`, so their outputs get mode 0600 whatever the umask. The CLI avoids them for this reason. The
  integrator may want the same `open(..., "x")` approach in both, so that library and CLI outputs agree.
- `record.read_container` reads any name but `.jsonl` as one JSON document. `record.write_container` writes anything
  but `.json` as JSONL. So a container written to `x.txt` cannot be read back. `khg-convert` avoids this with its
  suffix rule, and `khg-migrate` writes JSON for every name but `.jsonl`.
- The HIF layout depends on the input's key order (see `khg-convert`). A canonical layout for HIF would make the
  bytes a function of content alone, but then the packaged HIF files would no longer be reproduced byte for byte.

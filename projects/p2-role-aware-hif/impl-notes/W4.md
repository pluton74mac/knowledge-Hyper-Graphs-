# W4: `validate/` core

Step W4 of the [Implementation plan](../DESIGN.md#implementation-plan): the layer runner, the layer rule and the
pipelines, the registry, `engines.py` with closed offline resolvers, layers V, C and S, and the wiring of J (to
`jsonio`) and M (to `schema/`). It ports `khg_validate_proto.py`, `khg_engines_proto.py` and `make_registry.py`
(which the packaged `data/error-codes.json` replaces). Where DESIGN.md was ambiguous, the decisions below follow
`design-examples/` and the prototype. Nothing in DESIGN.md, `design-examples/` or `research/` was edited, and no file
of an earlier step was changed.

- single-fault engine containment (fastjsonschema's codes at the first rejecting step are among jsonschema's; one

`validate_container`, `validate_item`) runs as written.

## Decisions

### Runner and layer rule

- **The static table.** `layers/__init__.py` lists every layer module with its letter and owner, and `PIPELINES`
  lists the modules of each kind. The runner imports a module on first use and calls `run(ctx)`. A test checks that
  the letters of each pipeline, repeats dropped, equal the registry's pipeline (`c1`, `hif`, `role-convention`,
  `relation-schema`, `queue`, `c4`). Layer D has two modules, `d_decode` and `d_container`.
- **Stops.** A J or V error stops the run (§8.1). Otherwise every step runs (the full report). `run(stop="first")`
  stops after the first step with an error, as the prototype harness did; `Report.until_first_rejection()` gives the
  same findings from a full report, so the G2 harness can use either. `run(steps=...)` runs a subset (the loaders'
  `validate="profile"` is `j v h r p`, `"convention"` is `j h r`); J always runs, since it parses.
- **Failing steps.** Layers are written to read structurally broken input without raising. As a safety net, a step
  that raises after an earlier step reported an error is skipped and listed in `Report.skipped` (a later layer may
  not read what an earlier layer rejected). A step that raises on input without errors is a bug, and the exception
  propagates. The tests assert `skipped == []` on all 180 cases and on the malformed battery.
- **Letters outside the pipeline** (for example the M findings of an invalid embedded schema in a container run)
  rank after the pipeline's letters, in registry order. §8.1 does not cover them.
- **`validate` returns exactly `{ok, findings}`** (§10.2). `ok` is true when no finding is an error. `run` returns
  the full `Report` (kind, steps, stop, skipped, `first_layer`, `first_rejecting_step`).
- **Kinds.** The API kinds map to the registry's pipeline names: `record` and `container` to `c1`, `schema` to
  `relation-schema`, `item` to `c4`. `first_rejecting_layer` and `pipeline_letters` accept both, and `json` (the J
  cases).

### Inputs and arguments

- **A `str` is always a path** (as for the loaders, §5); raw content is passed as `bytes`. `os.PathLike` and
  packaged files (`read_bytes` and `name`) are paths. An unreadable path raises `OSError`; the CLI (W12) maps it to
  exit 2.
- **The auto kind** (V's `detect_kind`): lines by line 0's `kind` (`header`, `queue-header`, `c4-header`); an object
  with `header` and `records` is a container; `kind` `relation-schema` a schema, `entity` or `hyperedge` a record; a
  HIF-shaped object is `hif` when its metadata has `khg-profile`, else `role-convention` when it declares
  `role-convention`, else `hif` (so the user sees P001). An input whose kind cannot be told is **V001** ("format or
  profile id unknown"), and the run stops.
- **Bytes** for a container or the auto kind are read as JSONL when a one-document parse fails only with "Extra
  data". A `.jsonl` path is always JSONL, and so are queue and C4 files. A JSONL container becomes
  `{"header": line 0, "records": the rest}`, so its later findings are at `/records/<i>`; J findings are at
  `/lines/<n>`.
- **J on objects in memory.** J004, J005, J006 and J007 as for text; J001 for a value or key that is not JSON (a
  set, an object, an int key) and for nesting deeper than 512 levels (which also catches cycles). Tuples and
  non-dict mappings are read as arrays and objects, through a converted copy only when needed; the caller's object
  is never changed. A list is read as JSONL lines; a single object given as a queue or C4 file is a file of one line.
- **Arguments are not input.** `schema` is a `Schema` (used as is), or a document or path loaded with `load_schema`
  (J, V, M); an invalid one raises `ValidationError`. `bases` is `{document_id: container or path}`, one container,
  or an iterable of containers and paths (read with `record.read_container`). `doc_texts` is `{doc_id: text}`, a
  `khg-doc-texts` document or a path to one. Unknown `kind`, `engine`, `stop` or step names raise `ValueError`.
- **The wrappers** take `validate`'s keywords with the kind fixed. `validate_queue(q, *, schema, bases=None)` keeps
  `schema` required and also accepts `doc_texts` and `engine`.

### Layers

- **V** accepts the reader's major with a minor no newer than its own: `khg-record/1.0.x`, `khg-hif/1.0.x`,
  `khg-relation-schema/1.0.x` (W2's `version_findings`), `khg-queue/1.0.x`, and `khg-c4-items` 0.0.x and 0.1.x as in
  the prototype. Semver parts are ASCII without leading zeros. A HIF file without `khg-profile` passes V; a queue or
  C4 file without its header line passes V (Q008 and I are the owners').
- **C** runs the record schema on the container, `#/definitions/record` on a record, `#/definitions/hyperedge` on
  each queue payload (at `/lines/<n>/payload`), and the container that decoding left in a HIF run.
- **M** is W2's `meta_findings` (through the run's engine) followed by `python_findings`; the M checks were not
  re-ported. W2's and W3's small runners stay; `engines.py` is the general one.
- **S** ports `s_record`, `_s_value`, `_spans`, `_constraint` and `_nfc`, with the same checks, paths and finding
  order, so the 33 cases give exactly their `reported` codes. It reads broken structure without raising and does
  not repeat layer C: a non-string relation, non-list bindings or a malformed value are skipped. As in the
  prototype, the time-literal parse may emit C004 from the S step (another layer's code, §8.1).
- **S020 covers every string and every key** of every record, of the header, and of queue payloads and item
  entities (the prototype checked nine fields). Canonical JSON normalises every string to NFC, so any other string
  would change under hashing.
- **S026 judges a reason that is present.** A lifecycle record without `reason` is C012 alone; the prototype also
  reported S026 for the missing reason, but only in steps its harness never reached.
- **The run's schema** (`Context.relation_schema()`): the caller's, else the first embedded `relation-schema`
  record of a container, else a HIF file's `khg-schema-document`, else D009 ("no schema supplied and none
  embedded") at the kind's path, reported once, by the first step that asks (the S step, as in the prototype). A
  carried schema must pass `check_schema`; its V and M findings are reported at its path, and S cannot run then.
  A single record, a queue and C4 items carry no schema, so `validate_record(r)` without `schema` is D009. S020
  still runs without a schema.
- **Queue payloads** are checked as candidates (S003 is a warning). Entities resolve from `item.entities`, then from
  the base the header names, used only when `bases` supplies it under that `document_id` and its
  `record.container_sha256` equals the header's (`Context.queue_base()`); S005 runs on resolved entities only.

### Engines

- **Closed resolvers.** jsonschema gets a `referencing.Registry` of the six packaged schemas whose `retrieve`
  raises. fastjsonschema gets a handler map that answers every scheme, because fastjsonschema calls `urlopen` itself
  for a scheme it has no handler for (checked in 2.21.0 and 2.22.2). Both engines first walk every `$ref` reachable
  from the root and check its document and JSON pointer, so a bad reference fails closed at compile time with
  `engines.Unresolvable` (jsonschema would otherwise fail only when validation reaches it).
- **No mutation.** fastjsonschema's resolver rewrites `$ref` values in the documents it walks, so its handler serves
  copies; it compiles with `use_default=False` and `use_formats=False` (no schema uses `default` or `format`, and
  jsonschema checks no formats by default). A test checks that neither the instance nor the packaged documents
  change.
- **Codes.** `code_of(error.schema, error.validator)` for jsonschema and `code_of(exception.definition,
  exception.rule)` for fastjsonschema, else the H table (the prototype's, unchanged). Paths are RFC 6901 pointers
  (the prototype did not escape `~` and `/`); messages are cut to 200 characters.
- **Minimum versions.** `Registry.with_resources`, `Resolver.lookup` and `Unresolvable` exist in referencing
  0.28.4, the oldest jsonschema 4.18 allows; `use_default` and `use_formats` exist in fastjsonschema 2.21.0.
- **Speed.** jsonschema takes about 33 ms for the fixture container's C step (mostly `$ref` lookups), fastjsonschema
  about 3 ms, and layer S about 3 ms. Dereferencing the schemas once would make jsonschema 1.8 times faster; it was
  not done, to keep the registry the design describes.

### Observations on the design

- §8.1 says "if/then dispatch replaces `oneOf` and `anyOf`". The record, relation-schema, profile and C5 schemas
  use `anyOf` only inside `not`; the C4 draft keeps two `anyOf` (`as_of`: an instant or null) and one `oneOf` (a
  `put` or an `apply` event). All three carry I002, so both engines name I002. A test pins the three paths for W11a.
- The C5 output schema reports C010, a C code.
